# code_decl_to_abi — Testing Guide for Each Language

> *English translation of [code_decl_to_abi_TESTING_GUIDE.md](code_decl_to_abi_TESTING_GUIDE.md).*

> **Document purpose**: this file explains how to prepare the environment, start, run and verify the test programs generated by `code_decl_to_abi` across 17 target languages.
>
> **Prerequisite reading**: `code_decl_to_abi_USER_GUIDE.md` (especially Part II — Using the generated code).
>
> **Core principle**: the tests for every language follow the same two-process model — **start the service first, then start the call**; all print `[PASS]` / `[FAIL]` / `[SKIP]` lines to stdout; all use **exit code 0 for success and 2 for at least one failure** (some languages use 1 for fatal errors).
>
> **Document language**: Chinese.
>
> **Generated code language**: English.

## 1. General test conventions

### 1.1 The two-process model

Identical for all languages:

```
┌─────────────────────────────┐        ┌─────────────────────────────┐
│  Terminal 1 — Service        │        │  Terminal 2 — Call           │
│  listens on ipc:<Unit>_abi   │◄──────►│  connects to ipc:<Unit>_abi  │
│  P2P group: <Unit>_service_test_p2p  │        │  calls every API × every variant │
└─────────────────────────────┘        └─────────────────────────────┘
```

**Startup order is strict**: service first, then call. If the call is started first, it waits for the target service to come online (the wait differs per language, usually 10–30 seconds) and FAILs on timeout.

### 1.2 Endpoint and P2P naming

| Item | Value |
|----|-----|
| IPC endpoint | `ipc:<UnitName>_abi` |
| App name | `<UnitName>_abi` |
| P2P group name | `<UnitName>_service_test_p2p` |
| Client app name | `LF_TEST_CLIENT_SELF` |
| Helper APIs | `LF_TEST_WHOAMI`, `LF_TEST_ASK_SERVICE_CALL_ME`, `LF_TEST_REPORT_SERVICE_IDENTITY` |

These names are injected uniformly by the generator and are identical across languages, so **a service in any language can be tested by a call client in any language**.

### 1.3 Test variants per API

For every routine, the call test tries in sequence:

| Variant | Description |
|------|------|
| `(app call)` | Synchronous call by App name |
| `(app async)` | Asynchronous call by App name |
| `(app asyncSeq)` / `(app seq ...)` | Asynchronous sequential call by App name |
| `(uid call)` | Synchronous call by UID (the service UID must be obtained first) |
| `(uid async)` | Asynchronous call by UID |
| `(uid asyncSeq)` | Asynchronous sequential call by UID |
| `(p2pname call)` | Synchronous call by P2P group name |
| `(p2pname async)` | Asynchronous call by P2P group name |
| `(p2pname asyncSeq)` | Asynchronous sequential call by P2P group name |

Procedure-type routines only have the `notify` variant family.

### 1.4 Output and exit codes

| Output | Meaning |
|------|------|
| `[PASS] <label>` or `[PASS] <label> = <value>` | This variant passed |
| `[FAIL] <label> -- <reason>` | This variant failed |
| `[SKIP] <label> -- <reason>` | This variant was skipped (usually `no service UID`) |
| `[READY]` / `[OK] Service ready` | The service is ready |
| `[INFO]` | Diagnostic information |
| `[FATAL]` | Fatal error; the program exits |

| Exit code | Meaning |
|:------:|------|
| `0` | All PASS or SKIP |
| `2` | At least one FAIL |
| `1` | Environment preparation failed (missing dependency, missing runtime, prepare failed, etc.) |
| other | Language runtime or compile error |

### 1.5 Environment setup scripts

Except for Pascal (built into the test unit) and Python (module ships with `__main__`), every language comes with a `setup_*_tests.ps1` environment initialization script. **Run the script first, then run the tests.**

All scripts support `-Help`, which prints the language's full usage, prerequisites and failure exit codes.

## 3. Testing method per language

### 3.1 Pascal

**Test artifacts**

- `<Unit>_abi_service_test_unit.pas`
- `<Unit>_abi_call_test_unit.pas`

**Preparation**

No environment initialization script. You need a main program that hooks up the test unit. Minimal main program:

```pascal
program pascal_abi_test;
{$mode delphi}{$H+}
uses
  SysUtils,
  <Unit>_abi_service_test_unit,   // service side
  <Unit>_abi_call_test_unit;      // call side
begin
  if ParamStr(1) = 'service' then
    Start_Service_Test
  else
    Run_Call_Test;
end;
```

Or simply write a standalone main program that calls `Run_Call_Test`.

**Compile**

```bash
fpc -Fu<dir-with-lingofuse_import.pas> -Fu<dir-with-Z.Core.pas> \
    -Fu<dir-with-lingofuse_helper.pas> pascal_abi_test.pas
```

**Run**

Terminal 1:
```bash
./pascal_abi_test service
```
Wait for `[OK] service ready`, press Enter to stop.

Terminal 2:
```bash
./pascal_abi_test call
```

**Expected output**

- One `[PASS]` / `[FAIL]` / `[SKIP]` line per API × per variant
- `=== Summary ===` at the end, listing Pass / Fail / Skip
- Exit code 2 on failure

**Notes**

- `Test_<Api>` inside `Run_Call_Test` first tries `app call`, then the async, uid and p2pname variants in turn. The `service UID` is obtained through the cooperation of `LF_TEST_WHOAMI` and `LF_TEST_ASK_SERVICE_CALL_ME`; if these two APIs are not registered on the service side, all UID variants are SKIPped.
- The Pascal service test unit provides `Start_Service_Test` / `Stop_Service_Test` / `Is_Service_Test_Running`, so it can be embedded into an existing Pascal application.

### 3.2 Python

**Test artifacts**

- `<Unit>_abi_service_test.py`
- `<Unit>_abi_call_test.py`

**Preparation**

```bash
pip install py-lingofuse
```

Or (using the `lingofuse/` source directory of the v3 toolchain):

```bash
# PowerShell
$env:PYTHONPATH = "<v3>/src"
```

**Run**

Terminal 1:
```bash
python <Unit>_abi_service_test.py
```
Wait for `[OK] Service ready`, press Enter or Ctrl+C to stop.

Terminal 2:
```bash
python <Unit>_abi_call_test.py
```

**Expected output**

Same as Pascal. The Python version additionally prints `[INFO] total tests scheduled: N`.

**Notes**

- The Python test tries to call the async variants with `asyncio.run(...)`, so Python 3.7+ is required.
- UID variants require the service side to successfully respond to `LF_TEST_ASK_SERVICE_CALL_ME` (a reverse call into the client); if the service side does not register this API, UID variants are SKIPped.
- The service test listens on `ipc:<Unit>_abi` by default.

### 3.3 C++

**Test artifacts**

- `<Unit>_abi_service_main.cpp`
- `<Unit>_abi_call_main.cpp`
- `CMakeLists.txt`

**Preparation**

You need the directory containing `LingoFuse.h`, `LingoFuse.c`, `LingoFuse.hpp` and `lf_io.hpp`.

**Build**

```bash
cmake -S . -B build -DLINGOFUSE_CPP_DIR=<dir-with-LingoFuse.h>
cmake --build build --config Release
```

Or with plain `g++`:

```bash
g++ -std=c++17 -I<dir-with-LingoFuse.hpp> \
    <Unit>_abi_service.cpp <Unit>_abi_service_main.cpp \
    LingoFuse.c -o service_test -pthread
```

**Run**

Terminal 1:
```bash
./build/<Unit>_abi_service_test
```
Wait for `[OK] Service ready`, press Enter to stop.

Terminal 2:
```bash
./build/<Unit>_abi_call_test
```

**Notes**

- The C++ test program calls `LF_LoadLibrary()` at the start; on failure it prints `[FATAL] LF_LoadLibrary failed.` and exits. In that case put `LingoFuse64.dll` / `liblingofuse.so` / `liblingofuse.dylib` next to the executable, or on the OS loader search path.
- MSVC users must add `/utf-8`, otherwise the description strings are encoded with the system codepage and will not match UTF-8.
- The C++ side supports the async variants (`*_Async`, `*_AsyncSequenced`) as well as all 9 combinations of UID / P2PName.

### 3.4 C#

**Test artifacts**

- `<Unit>_abi_service_test___.cs`
- `<Unit>_abi_call_test___.cs`

**Preparation**

Both test programs need their own `.NET console project` (they cannot be mixed into the same project as the library files, otherwise `CS0017: Program has more than one entry point` is triggered).

```bash
# service side
dotnet new console -o service_test
cd service_test
cp ../<Unit>_abi_service.cs .
cp ../<Unit>_abi_service_test___.cs Program.cs
cp ../LingoFuse64.dll .
dotnet run
```

**Run**

Terminal 1:
```bash
cd service_test
dotnet run
```

Terminal 2:
```bash
cd call_test     # created the same way
dotnet run
```

**Notes**

- The C# test uses `DllImportResolver` to locate `LingoFuse64.dll` / `lingofuse64.dll` (Windows 64-bit) and similar runtimes automatically, so putting the DLL in the working directory of `dotnet run` is enough.
- `ABI.Timeout` defaults to 5000 ms; adjust it by editing `ABI.Timeout = 30000;` in `Program.cs`.
- `ABI.TargetApp` defaults to `<Unit>_abi`; for cross-machine or cross-process use, both sides must agree.

### 3.5 Rust

**Test artifacts**

- `<Unit>_abi_service_test.rs`
- `<Unit>_abi_call_test.rs`
- `setup_rust_tests.ps1`
- `Cargo.toml` (created by the setup script)

**Preparation**

```powershell
.\setup_rust_tests.ps1 -LingofuseDir <dir-with-lingofuse-crate> -RunSmoke
```

The script will:

1. Copy the `.rs` files into `src/` and `examples/`;
2. Create `Cargo.toml` and inject `lingofuse = { path = "<LingofuseDir>" }`;
3. Scan for and clean up stale copies;
4. Run `cargo build` (plus `cargo build --examples` with `-RunSmoke`).

**Run**

Terminal 1:
```bash
cargo run --example service_test
```
Wait for `[OK] Service ready`, press Enter to stop.

Terminal 2:
```bash
cargo run --example call_test
```

**Notes**

- The Rust test uses `std::sync::mpsc` and `catch_unwind` to protect async callbacks; any panic is caught and turned into `[FAIL]`.
- `setup_rust_tests.ps1` has `-Force` to overwrite old files; `-RunSmoke` compiles the examples; `-Help` shows full usage.
- If `cargo build` reports that the `lingofuse` crate cannot be found, check whether the `path` in `Cargo.toml` points to the directory containing `Cargo.toml` and `src/lib.rs`.

### 3.6 Go

**Test artifacts**

- `<Unit>_abi_service_test.go`
- `<Unit>_abi_call_test.go`
- `setup_go_tests.ps1`
- `go.mod` / `go.sum` (generated by the setup script)

**Preparation**

```powershell
.\setup_go_tests.ps1 -LingoFuseGo <dir-with-lingofuse-go-module> -Force
```

The script will:

1. Organize the library files (`<Unit>_abi_call.go` / `<Unit>_abi_service.go`) and the two test main programs into `.go_clean_build/`;
2. Place the test programs in `<Unit>_abi_service_test/main.go` and `<Unit>_abi_call_test/main.go`;
3. Generate `go.mod` and inject `replace github.com/PassByYou888/LingoFuse/go => <path>`;
4. Run `go mod tidy`, `gofmt`, `go build ./...`, `go vet ./...`.

**Run**

Terminal 1:
```bash
cd .go_clean_build
go run ./<Unit>_abi_service_test
```

Terminal 2:
```bash
cd .go_clean_build
go run ./<Unit>_abi_call_test
```

**Notes**

- Go test output uses the `[PASS]` / `[FAIL]` / `[SKIP]` prefixes; the three counters `_g.pass` / `_g.fail` / `_g.skip` are summarized at the end.
- Internally the test waits for async callbacks with `chan callResult[T]` and `select`, with a 10-second timeout.
- The `-GOPROXY` script parameter specifies the Go module proxy (default `https://goproxy.cn,direct`); `-Clean` deletes `.go_clean_build/` after success.
- If it reports `stale Go files detected`, the generated `.go` files are outdated (containing Pascal type names) and must be regenerated.

### 3.7 Java

**Test artifacts**

- `<Unit>AbiServiceMain.java`
- `<Unit>AbiCallTestMain.java`
- `pom.xml`
- `setup_java_tests.ps1` + `run_java_service.ps1` / `run_java_call.ps1`

**Preparation**

```powershell
.\setup_java_tests.ps1 -LingoFuseJava <dir-with-lingofuse-java-project>
```

JDK 22+ and Maven 3.9+ are required. The script will:

1. Validate the `LingoFuseJava` directory and `lingofuse*.jar` (automatically running `mvn -Dmaven.test.skip=true package` if missing);
2. Copy `pom.xml`, `lingofuse.jar` and the four `.java` files into `.java_clean_build/`;
3. Copy `LingoFuse64.dll` / `lingofuse.so` / `lingofuse.dylib`;
4. Run `mvn -q -DskipTests compile`.

**Run**

Terminal 1:
```powershell
.\run_java_service.ps1
```

Terminal 2:
```powershell
.\run_java_call.ps1
```

Or manually:

```bash
cd .java_clean_build
mvn -q -DskipTests compile exec:java -Dexec.mainClass="lingofuse.abi.<lower_unit>.<Unit>AbiServiceMain"
```

**Notes**

- The Java service test listens on `ipc:<Unit>_abi`; the three constants `kTargetApp`, `kTargetP2P`, `kEndpoint` are injected at the start of the `main` method.
- The test waits for async callbacks with `CountDownLatch` + `AtomicReference`, with a 5000 ms timeout.
- `libraryLoader.selectPlatformFileName()` selects the platform file name automatically; on failure it reports `[FATAL] LingoFuse native library not found`.
- `setup_java_tests.ps1` supports `-Force` / `-Clean` / `-Help`; `-Clean` deletes `.java_clean_build/` after success.

### 3.8 Node.js

**Test artifacts**

- `<Unit>_abi_service_test.js`
- `<Unit>_abi_call_test.js`
- `setup_node_tests.ps1`
- `package.json` (generated by the setup script)

**Preparation**

```powershell
.\setup_node_tests.ps1 -LingoFuseJs <dir-with-lingofuse-js> -RunSmoke
```

The script will:

1. Check `LingoFuseJs/node_modules/koffi` (running `npm install` automatically if missing);
2. Write `package.json` with `lingofuse-js` pointing at `LingoFuseJs`;
3. Run `npm install`;
4. Syntax-check the four `.js` files with `node --check`;
5. With `-RunSmoke`, start the service test in the background, run the call test in the foreground and verify the exit code.

**Run**

Terminal 1:
```bash
node <Unit>_abi_service_test.js
```
Wait for `[OK] service ready`.

Terminal 2:
```bash
node <Unit>_abi_call_test.js
```

**Notes**

- The Node.js test uses `process.on('SIGINT')` to catch Ctrl+C and shut down gracefully.
- `_race(promise, timeoutMs, label)` wraps every async call; a timeout becomes `[FAIL]`.
- The service side registers three helper APIs (`LF_TEST_WHOAMI`, `LF_TEST_ASK_SERVICE_CALL_ME`, `LF_TEST_REPORT_SERVICE_IDENTITY`) for UID discovery and reverse calls.
- If `npm install` fails, `setup_node_tests.ps1` prints the full error and exits 1.

### 3.9 TypeScript

**Test artifacts**

- `<Unit>_abi_service_test.ts`
- `<Unit>_abi_call_test.ts`
- `setup_ts_tests.ps1`
- `tsconfig.json` / `package.json` (generated by the setup script)

**Preparation**


The script will:

4. Run `npm install`;
5. Type-check with `tsc --noEmit`;
6. With `-RunSmoke`, start the service in the background and run the call test in the foreground.

**Run**

**Default (run directly with tsx)**:

Terminal 1:
```bash
node node_modules/tsx/dist/cli.mjs <Unit>_abi_service_test.ts
```

Terminal 2:
```bash
node node_modules/tsx/dist/cli.mjs <Unit>_abi_call_test.ts
```

**`-Compiled` mode (precompiled with tsc)**:

```powershell
.\setup_ts_tests.ps1 -LingoFuseTs <...> -Compiled
# then run with node dist/<Unit>_abi_service_test.js
```

**Notes**

- TypeScript's `reportIdentityCb` must be registered inside `_koffi.register(...)`; `koffi` is `lingofuse-ts`'s internal binding.
- It depends on the `LfCallFuncPtr` / `LfNotifyFuncPtr` pointer types, exported by `lingofuse-ts`.
- If the `LingoFuseTs` path contains Chinese characters or spaces, use `-SkipAutoLink` and create the junction manually.

### 3.10 Erlang

**Test artifacts**

- `<Unit>_abi_service_main.erl`
- `<Unit>_abi_call_main.erl`
- `setup_erlang_tests.ps1`
- `rebar.config` / `<Unit>_abi.app.src` (generated by the setup script)

**Preparation**

**OTP 27+** is required (`erl`, `erlc` and `escript` must all be on PATH).

```powershell
.\setup_erlang_tests.ps1 -LingofuseEbin <dir-with-lingofuse.beam> -RunSmoke
```

The script will:

1. Validate `lingofuse.beam` (auto-searching `<dir>` / `<dir>/lingofuse/ebin` / `<dir>/_build/default/lib/lingofuse/ebin` / `<dir>/ebin`);
2. Verify OTP ≥ 27;
3. Organize the `.erl` files into `src/`;
4. Generate `rebar.config` and `.app.src`;
5. Compile with `rebar3` (preferred) or `erlc` (fallback);
6. With `-RunSmoke`, start the service test, run the call test and check the exit code.

**Run**

Terminal 1:
```bash
erl -noshell -pa <lingofuse-ebin> -pa _build/default/lib/<Unit>_abi/ebin \
    -eval "<Unit>_abi_service_main:main([])."
```
Wait for `[OK] service ready`.

Terminal 2:
```bash
erl -noshell -pa <lingofuse-ebin> -pa _build/default/lib/<Unit>_abi/ebin \
    -eval "<Unit>_abi_call_main:main([])."
```

**Notes**

- Both main programs are `-module('<Unit>_abi_service_main')` style, with `main([])` as the entry point.
- The service side listens on `ipc:<Unit>_abi`; after start, `main` calls `timer:sleep(15000)` and then `loop(App)` (giving the service a 15-second startup grace period).
- On the call side, `run_tests/1` wraps each variant with `run_sync_test` / `run_async_test` / `run_uid_*` / `run_p2p_*`; UID/P2P routing timeouts are classified as SKIP rather than FAIL.
- If the `*.beam` files end up in the wrong `ebin` after compiling, check whether `rebar3 compile` succeeded, or use manual `erlc -o ebin src/*.erl`.

### 3.11 Julia

**Test artifacts**

- `<Unit>_abi_service_test.jl`
- `<Unit>_abi_call_test.jl`
- `setup_julia_tests.ps1` + `run_julia_service.ps1` / `run_julia_call.ps1`
- `Project.toml` / `runtests.jl` (generated by the setup script)

**Preparation**

**Julia 1.9+** is required, with at least 2 threads enabled (the test checks `Threads.nthreads() < 2` and errors out).

```powershell
.\setup_julia_tests.ps1 -LingoFuseJulia <dir-with-lingofuse-julia-package>
```

The script will:

2. Copy the four `.jl` files plus `Project.toml` / `runtests.jl` into `.julia_clean_build/`;
3. Copy `LingoFuse64.dll` / `liblingofuse.so` / `liblingofuse.dylib`;
4. Install dependencies with `Pkg.develop(path="<LingoFuseJulia>")`.

**Run**

Terminal 1:
```powershell
.\run_julia_service.ps1
```
Equivalent to `julia --project=. --threads=2 <Unit>_abi_service_test.jl --serve-only`.

Terminal 2:
```powershell
.\run_julia_call.ps1
```

**Notes**

- **`--threads=2` is mandatory**, otherwise the script errors out immediately.
- `--serve-only` mode only runs the service and skips the self-loop test; use it together with `run_julia_call.ps1` for cross-process testing.
- If `loader.jl` cannot find the runtime library, set the environment variable `LINGOFUSE_LIBRARY=<absolute path to .dll>`.
- `setup_julia_tests.ps1`'s `-Clean` deletes `.julia_clean_build/` after success.

### 3.12 Zig

**Test artifacts**

- `<Unit>_abi_service_test.zig`
- `<Unit>_abi_call_test.zig`
- `setup_zig_tests.ps1`
- `build.zig` / `build.zig.zon` (generated by the setup script)

**Preparation**

## 4. Cross-language testing

The ABI wire protocol is language-independent: the service and call of any two languages can interconnect.

### 4.1 Steps

1. Choose language A as the service and language B as the call;
2. Generate all artifacts for both languages from **the same source unit**;
3. Prepare the environment per A's `setup_*_tests.ps1 -Help` and start A's **service test**;
4. Prepare the environment per B's `setup_*_tests.ps1 -Help` and start B's **call test**;
5. Observe B's `[PASS]` / `[FAIL]` / `[SKIP]` output.

### 4.2 Common combinations

| Service language | Call language | Notes |
|--------------|-----------|------|
| Pascal | Python / C++ / C# / Rust / … | Pascal as the reference implementation, good for comparison |
| C++ | Python / Go / Java | Performance comparison scenarios |
| Python | any language | Fast prototype validation |
| Rust | any language | Memory safety + high-performance scenarios |

### 4.3 Key points

- **Both sides must be generated from the same source unit**. Different source units may produce different API names and type tables.
- **UID / P2PName variants require `LF_TEST_WHOAMI` and `LF_TEST_ASK_SERVICE_CALL_ME` to be registered on the service side**. In a cross-language setup, if B's call test triggers these two helper APIs while A's service has not registered them, the UID variants are SKIPped (not counted as FAIL).
- **The endpoint name `<Unit>_abi` is globally unique**: running several test groups at the same time interferes with each other. Before each group, confirm there is no leftover service using `ps aux | grep` or Task Manager.

## 5. Troubleshooting steps when a test fails

### 5.1 Quick triage

1. **Check whether the service printed `[OK] Service ready`**. If not, the problem is in the service startup phase;
2. **Check whether the call connected to the service within 30 seconds**. If not, check whether the endpoint `ipc:<Unit>_abi` matches;
3. **Look at the label and reason of `[FAIL]`**. The label carries the variant name (`app call` / `uid async` / …), and the reason is usually the specific exception message.

### 5.2 Classification by symptom

| Symptom | Possible cause | Fix |
|------|----------|------|
| `[FATAL] LF_LoadLibrary failed` | The runtime library is not next to the executable or on the loader search path | See `code_decl_to_abi_USER_GUIDE.md` Chapter 13 |
| `[FATAL] createApp failed` | LingoFuse runtime version mismatch | Use a runtime matching the binding |
| `[FATAL] prepareDone failed` | Endpoint name conflict, or the service is not started | Check the endpoint name; confirm the service is running |
| `[FAIL] <Api>(app call) -- nil response` | Target App name mismatch, or the timeout is too short | Check `TargetApp` on both sides; raise the timeout |
| `[FAIL] <Api>(app call) -- input truncated` | The two sides disagree on the field count | Confirm both sides were generated from the same model |
| `[FAIL] <Api>(uid call)` frequently | `LF_TEST_ASK_SERVICE_CALL_ME` not registered on the service side | Add that helper API on the service side |
| Everything `[SKIP]` | `LF_TEST_WHOAMI` not registered on the service side | Add that helper API on the service side |
| Single-language PASS, cross-language FAIL | Type tables differ between the two sides | Check `ABI_Type_To_<Lang>_Decl` on both sides |
| `[FAIL] <Api>(app async) -- timeout` | The async callback called `LF_Call` and deadlocked | Dispatch the call inside the callback to a separate thread |

### 5.3 Collecting diagnostic information

- **Service-side log**: `setup_*_tests.ps1 -RunSmoke` saves the service stdout/stderr to `smoke_service.out.log` / `smoke_service.err.log` (the file names may differ slightly per language).
- **Call-side log**: read the terminal output directly, or redirect it to a file.
- **Runtime log**: set the environment variable `LF_LOG=1` (if the binding supports it) to enable LingoFuse internal logging.

### 5.4 Reproducing a minimal case

If a particular API fails, try:

1. **Run only that API's `app call` variant** (temporarily edit the call test's `test_<Api>` function to drop the uid / p2pname variants);
2. **Run only that API's `app notify` variant** (if it is a procedure);
3. **Check whether the `<Api>` stub `internal_call_<Api>` on the service side** is still `TODO` / returning 0.

### 5.5 Ultimate debugging

- Capture the actual byte stream with Wireshark or LingoFuse's built-in logging, and compare it byte by byte against the wire protocol description in `code_decl_to_abi_USER_GUIDE.md` Chapter 16.
- If you suspect a runtime problem, verify `LF_Call` / `LF_Notify` separately with a minimal C++ or Pascal test program.
