## 1. Terminology and variant naming rules

### 1.1 The role of the Call library

The Call library is responsible for interactions **initiated actively by the caller**:

- firing a call at the service and waiting for the result (sync)
- firing a call without blocking the thread (async / Future / Promise / Task)
- firing a call with guaranteed ordering on the connection (asyncSeq / sequenced)
- locating the service by UID or P2P group name
- sending a notification (notify) without waiting for a return value

### 1.2 Variant naming rules (uniform across languages)

The table below lists all variants the generator produces for each API (using the function `Foo` as an example):

| Variant | Semantics | Notes |
|------|------|------|
| `Foo` | **App synchronous call** | Locates the service by `ABI_TARGET_APP`, blocks until a result arrives |
| `Foo_Async` | **App asynchronous call** | Does not block the thread; returns the result via callback / Future / Promise |
| `Foo_AsyncSequenced` | **App asynchronous sequential call** | Same as `Async`, but guarantees ordered dispatch on the same connection |
| `Foo_UID_Call` | **UID synchronous call** | Locates the service by its 32-byte UID, blocks |
| `Foo_UID_Async` | **UID asynchronous call** | Same as above, asynchronous |
| `Foo_UID_AsyncSequenced` | **UID asynchronous sequential call** | Same as above, with ordering guaranteed |
| `Foo_P2PName_Call` | **P2P group name synchronous call** | Locates the service by P2P group name, blocks |
| `Foo_P2PName_Async` | **P2P group name asynchronous call** | Same as above, asynchronous |
| `Foo_P2PName_AsyncSequenced` | **P2P group name asynchronous sequential call** | Same as above, with ordering guaranteed |

Procedure APIs (no return value) only generate the notify variant family:

| Variant | Semantics |
|------|------|
| `Foo` | App notification (`notify`) |
| `Foo_SequencedNotify` | App sequential notification |
| `Foo_UID_Notify` | UID notification |
| `Foo_UID_SequencedNotify` | UID sequential notification |
| `Foo_P2PName_Notify` | P2P group name notification |
| `Foo_P2PName_SequencedNotify` | P2P group name sequential notification |

### 1.3 On "asynchronous notify"

**notify by definition means "send and do not wait for a return value"**, so from the caller's point of view all notify calls are non-blocking:

- calling `Foo()` (an App notification) returns immediately;
- whether, when, or with what failure the service executes it is invisible to the caller.

**What `SequencedNotify` changes**: it guarantees that on the same LingoFuse connection multiple notifies are delivered to the service in the caller's call order, without being reordered by the worker thread pool. That is "stronger asynchrony", but it is **still fire-and-forget**.

**The call library itself provides no "asynchronous notify reception"** — receiving is the service library's job (`LF_RegisterNotify` + callback). The call library only sends.

Therefore below:
- "**supports asynchronous notify**" = supports all 6 notify variants (including sequenced)
- "**supports asynchronous call**" = supports the async / asyncSeq variants (a request-response pattern that does not block the thread)

| File | Purpose |

### 3.1 Pascal

**Call library file**: `<Unit>_abi_call_unit.pas`

**Supported variants**

Function (15):
- `Foo`
- `Foo_Async` / `Foo_Async_P`
- `Foo_AsyncSequenced` / `Foo_AsyncSequenced_P`
- `Foo_UID_Call`
- `Foo_UID_Async` / `Foo_UID_Async_P`
- `Foo_UID_AsyncSequenced` / `Foo_UID_AsyncSequenced_P`
- `Foo_P2PName_Call`
- `Foo_P2PName_Async` / `Foo_P2PName_Async_P`
- `Foo_P2PName_AsyncSequenced` / `Foo_P2PName_AsyncSequenced_P`

Procedure (6):
- `Foo`
- `Foo_SequencedNotify`
- `Foo_UID_Notify`
- `Foo_UID_SequencedNotify`
- `Foo_P2PName_Notify`
- `Foo_P2PName_SequencedNotify`

**Development platform**

| Item | Requirement |
|------|------|
| Compiler | Free Pascal 3.2+ or Delphi 10.4+ |
| Language mode | Delphi mode (`{$mode delphi}`) |
| Source encoding | UTF-8 (`{$CODEPAGE UTF8}`) |

**OS**: Windows / Linux / macOS.

**Dependencies**

| Dependency | How to include |
|------|----------|
| `lingofuse_import.pas` | `-Fu<dir-with-lingofuse_import.pas>` |
| `Z.Core` | `-Fu<dir-with-Z.Core.pas>` |
| Runtime DLL / SO / DYLIB | Next to the executable, or on the loader search path |

**Integration code**

```pascal
uses
  <Unit>_abi_call_unit;

var
  Result: Integer;
begin
  ABI_Timeout := 5000;
  try
    Result := Foo(10, 20);                                   // App sync
    Result := Foo_UID_Call(MyUid, 10, 20);                   // UID sync
    Result := Foo_P2PName_Call('my_p2p_group', 10, 20);      // P2P sync
  except
    on E: EABI_RemoteError do
      Writeln('remote error: ', E.Message);
  end;
end;
```

**Async call (method callback)**

```pascal
type
  TFooHandler = class
  public
    procedure OnSuccess(const Value: Integer);
    procedure OnError(const ErrorMsg: string; Code: Integer);
  end;

var
  H: TFooHandler;
begin
  H := TFooHandler.Create;
  try
    Foo_Async(10, 20, H.OnSuccess, H.OnError);
  finally
    H.Free;
  end;
end;
```

**Async call (nested proc callback)**

```pascal
var
  Done: Boolean = False;
begin
  Foo_Async_P(10, 20,
    procedure(const Value: Integer)
    begin
      Done := True;
    end,
    procedure(const ErrorMsg: string; Code: Integer)
    begin
      Done := True;
    end);
end;
```

**Cautions**

- **Difference between `_M` and `_P`**: `_M` is an object method (`of object`), `_P` is a nested proc / reference to. Both FPC and Delphi support them; choose based on whether the callback needs to capture context.
- **Callback thread**: callbacks run on a worker thread; **do not** call `LF_Call` / `LF_Notify` inside a callback (it deadlocks), and **do not** touch UI inside a callback (`TThread.Synchronize` is required).
- **Timeout**: `ABI_Timeout` is a global (unit-level) variable, defaulting to 5000 ms.
- **Error handling**: synchronous calls raise `EABI_RemoteError` on failure; asynchronous calls report through the `OnError` callback.

### 3.2 Python

**Call library file**: `<Unit>_abi_call.py`

**Supported variants**

Function (15):
- `Foo` (synchronous, returns `int` / `float` / `str`)
- `Foo_UID_Call`, `Foo_P2PName_Call` (synchronous)
- `Foo_Async`, `Foo_AsyncSequenced` (return `CallFuture`)
- `Foo_Aio`, `Foo_Sequenced_Aio` (`async def`)
- `Foo_UID_Async`, `Foo_UID_AsyncSequenced`, `Foo_UID_Aio`, `Foo_UID_Sequenced_Aio`
- `Foo_P2PName_Async`, `Foo_P2PName_AsyncSequenced`, `Foo_P2PName_Aio`, `Foo_P2PName_Sequenced_Aio`

Procedure (6):
- `Foo`
- `Foo_SequencedNotify`
- `Foo_UID_Notify`
- `Foo_UID_SequencedNotify`
- `Foo_P2PName_Notify`
- `Foo_P2PName_SequencedNotify`

**Development platform**

| Item | Requirement |
|------|------|
| Python | CPython 3.7+ (`asyncio` needs 3.7+) |
| Optional dependencies | none (`async_support` is implemented internally) |

**OS**: Windows / Linux / macOS (every platform CPython supports).

**Dependencies**

| Dependency | How to include |
|------|----------|
| The `lingofuse` Python package | `pip install py-lingofuse` or `PYTHONPATH=<v3>/src` |

**Integration code**

```python
from lingofuse._lf_native import (
    LF_ResetPrepare, LF_PrepareClient, LF_PrepareDone,
    LF_ExitMainThread, LF_Shutdown,
)
from lingofuse.lf_io import cstr
import <Unit>_abi_call as abi

LF_ResetPrepare()
LF_PrepareClient(cstr("ipc:<Unit>_abi"), None)
if LF_PrepareDone() != 1:
    raise SystemExit(1)

try:
    abi.ABI_TIMEOUT = 5000

    # synchronous App call
    print(abi.Foo(10, 20))

    # synchronous UID / P2P calls
    print(abi.Foo_UID_Call(my_uid_bytes, 10, 20))
    print(abi.Foo_P2PName_Call("my_p2p_group", 10, 20))

    # async Future
    fut = abi.Foo_Async(10, 20)
    print(fut.result(timeout=5.0))

    # async/await
    import asyncio
    print(asyncio.run(abi.Foo_Aio(10, 20)))

    # sequential notify
    abi.Foo_SequencedNotify(10, 20)
finally:
    LF_ExitMainThread()
    LF_Shutdown()
```

**Cautions**

- **`Foo_Async` return value**: a `CallFuture` supporting `.result(timeout=)`, `.add_done_callback(fn)`, `.cancel()`.
- **`Foo_Aio`**: an `async def` that must be awaited inside `asyncio.run()` or an already running event loop.
- **`on_result` callback**: `Foo_Async(..., on_result=fn, user_data=ud)` allows callback-style use with `fn(result, error, user_data)`; when `on_result` is omitted a Future is returned.
- **Timeout**: `abi.ABI_TIMEOUT` (a module-level variable); 0 means no timeout.
- **UID type**: `bytes` (32 bytes), a hex string (64 characters), or the `{bytes: Uint8Array(32)}` form (handled by `normalize_uid`).
- **Python GIL**: async callbacks execute in `async_support`'s thread pool; do not do blocking IO inside them; running `asyncio.run` on a non-main thread requires an event loop policy.

**Development platform**

| Optional build system | CMake 3.15+ |

**OS**: Windows / Linux / macOS.

**Dependencies**

| Dependency | How to include |
|------|----------|
| `LingoFuse.hpp` / `lf_io.hpp` | `-I<dir-with-headers>` |
| `LingoFuse.c` | Compile into the project (as the `lingofuse_c_wrapper` static library in CMake) |

**Integration code**

```cpp
#include "<Unit>_abi_call.hpp"
#include "LingoFuse.hpp"

int main() {
    if (LF_LoadLibrary() != 1) {
        std::fprintf(stderr, "[FATAL] LF_LoadLibrary failed\n");
        return 1;
    }

    <Unit>_abi::ABI_TargetApp = "<Unit>_abi";
    <Unit>_abi::ABI_Timeout   = 5000;

    try {
        // synchronous App call
        auto v = <Unit>_abi::Foo(10, 20);

        // synchronous UID / P2P calls
        std::array<std::uint8_t, 32> uid = {/* 32 bytes */};
        auto u = <Unit>_abi::Foo_UID_Call(uid, 10, 20);
        auto p = <Unit>_abi::Foo_P2PName_Call("my_p2p_group", 10, 20);

        // asynchronous
        <Unit>_abi::Foo_Async(10, 20, [](lingofuse::AsyncResult r) {
            if (r.err) {
                std::printf("[FAIL] %s\n", r.err->what());
            } else {
                // r.value is a DataHandle and must be decoded
            }
        });
    } catch (const <Unit>_abi::EABI_RemoteError& e) {
        std::fprintf(stderr, "remote error: %s\n", e.what());
    }

    LF_FreeLibrary();
    return 0;
}
```

**CMake integration**

```cmake
cmake_minimum_required(VERSION 3.15)
project(my_app LANGUAGES CXX C)
set(CMAKE_CXX_STANDARD 17)

find_package(Threads REQUIRED)

# compile the C wrapper
add_library(lingofuse_c_wrapper STATIC
    ${LINGOFUSE_CPP_DIR}/LingoFuse.c)
target_include_directories(lingofuse_c_wrapper PUBLIC ${LINGOFUSE_CPP_DIR})

# compile the call library
add_library(<Unit>_abi_call STATIC <Unit>_abi_call.cpp)
target_include_directories(<Unit>_abi_call PUBLIC ${CMAKE_CURRENT_SOURCE_DIR})
target_link_libraries(<Unit>_abi_call PUBLIC lingofuse_c_wrapper Threads::Threads)

# your application
add_executable(my_app main.cpp)
target_link_libraries(my_app PRIVATE <Unit>_abi_call)
```

**Cautions**

- **`LF_LoadLibrary()` must be called first**: the C++ side does not auto-load the runtime; a return of 1 means success.
- **MSVC**: `/utf-8` is mandatory, otherwise the encoding of the API description strings is wrong.
- **`EABI_RemoteError`**: thrown when a synchronous call fails; carries `what()`.
- **`std::function<void(lingofuse::AsyncResult)>`**: the async callback signature; `AsyncResult` contains `err` (`std::optional<std::string>`) and `value` (`DataHandle`).
- **UID type**: `std::array<std::uint8_t, 32>`.
- **Callback thread**: runs on a worker thread; no blocking LingoFuse calls inside the callback.

**Integration code**

```csharp
using System;
using System.Threading.Tasks;
using lingofuse;
using <Unit>_abi_call;

class Program
{
    static async Task Main()
    {
        ABI.TargetApp = "<Unit>_abi";
        ABI.Timeout   = 5000;

        // synchronous App call
        int v = ABI.Foo(10, 20);

        // synchronous UID / P2P
        var uid = P2PUid.FromBytes(myUidBytes);
        int u = ABI.Foo_UID_Call(uid, 10, 20);
        int p = ABI.Foo_P2PName_Call("my_p2p_group", 10, 20);

        // asynchronous (Task)
        int a  = await ABI.Foo_Async(10, 20);
        int as_ = await ABI.Foo_AsyncSequenced(10, 20);

        // async UID
        int au = await ABI.Foo_UID_Async(uid, 10, 20);

        // notify
        ABI.Foo(10, 20);                      // App notify
        ABI.Foo_SequencedNotify(10, 20);
        ABI.Foo_UID_Notify(uid, 10, 20);
        ABI.Foo_P2PName_Notify("my_p2p_group", 10, 20);
    }
}
```

**Cautions**

- **`ABI.TargetApp` / `ABI.Timeout`**: static fields of the `ABI` class, globally effective; anything changed affects all subsequent calls.
- **`P2PUid`**: the wrapper type for a 32-byte UID, supporting `FromBytes` / `ToByteArray` / `IsEmpty`.
- **Async implementation**: `Foo_Async` returns `Task<T>`, internally based on `TaskCompletionSource`; `await` works directly.
- **`DllImportResolver`**: automatically selects `LingoFuse64.dll` / `LingoFuse32.dll` / `liblingofuse.so` / `liblingofuse.dylib` per platform.
- **Callback thread**: C#'s async callbacks are already marshalled to the thread pool through `TaskCompletionSource`; a later `.ConfigureAwait(false)` avoids deadlocks.

**Integration code**

```rust
use <Unit>_abi::call;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    call::ABI_TARGET_APP
        .write()
        .unwrap()
        .clone_from(&"<Unit>_abi".to_string());
    call::ABI_TIMEOUT.store(5000, std::sync::atomic::Ordering::SeqCst);

    // synchronous App call
    let v: i32 = call::Foo(10, 20)?;

    // synchronous UID / P2P
    let uid = lingofuse::uid::Uid::from_bytes(my_uid_bytes);
    let u: i32 = call::Foo_UID_Call(uid, 10, 20)?;
    let p: i32 = call::Foo_P2PName_Call("my_p2p_group", 10, 20)?;

    // asynchronous
    let (tx, rx) = std::sync::mpsc::channel();
    call::Foo_Async(10, 20, move |r| { let _ = tx.send(r); })?;
    let a = rx.recv_timeout(std::time::Duration::from_secs(10))??;

    // notify
    call::Foo(10, 20)?;                              // App notify
    call::Foo_SequencedNotify(10, 20)?;
    call::Foo_UID_Notify(uid, 10, 20)?;
    call::Foo_P2PName_Notify("my_p2p_group", 10, 20)?;

    Ok(())
}
```

**Cautions**

- **`ABI_TARGET_APP` / `ABI_TIMEOUT`**: static variables of type `RwLock<&'static str>` / `AtomicU64`.
- **Error type**: `Result<T, lingofuse::error::Error>`; `Error` contains an `ErrorCode` enum (`CallFailed` / `ReadFailed` / `NullHandle` / `Timeout` etc.).

- **panic safety**: the library wraps callbacks with `catch_unwind`, but your own callback should avoid panicking too.

```dart
import 'dart:async';
import 'package:lingofuse/lingofuse.dart';
import '<Unit>_abi_call.dart' as abi;

Future<void> main() async {
  await BridgeHost.start();
  Framework.setOptQuiet(true);

  abi.ABI_TARGET_APP = '<Unit>_abi';
  abi.ABI_TIMEOUT_MS = 5000;

  // synchronous call wrapped as a Future (Isolate.run)
  final v = await abi.Foo(10, 20);

  // sequential call
  final as_ = await abi.FooSequenced(10, 20);

  // callback-style async
  await _waitAsync('FooAsync', (finish) {
    abi.FooAsync(10, 20, finish);
  });

  // synchronous UID / P2P (returns a Future)
  final u = await abi.FooByUid(uidBytes, 10, 20);
  final p = await abi.FooByP2PName('my_p2p_group', 10, 20);

  // notify
  abi.FooNotify(10, 20);
  abi.FooSequencedNotify(10, 20);
  abi.FooNotifyByUid(uidBytes, 10, 20);
  abi.FooNotifyByP2PName('my_p2p_group', 10, 20);

  BridgeHost.instance.stop();
}

Future<void> _waitAsync<T>(String label, void Function(void Function(T?, String?)) starter) async {
  final completer = Completer<T?>();
  starter((result, error) {
    if (completer.isCompleted) return;
    if (error != null) {
      completer.completeError(StateError(error));
    } else {
      completer.complete(result);
    }
  });
  await completer.future.timeout(const Duration(seconds: 10));
}
```

**Cautions**

- **`ABI_TARGET_APP` / `ABI_TIMEOUT_MS`**: module-level `String` / `int` variables.
- **`Foo` returns a `Future`**: although the call is synchronous internally, it is run on a separate isolate via `Isolate.run`, so the main isolate does not block.
- **`FooAsync` is a callback**: `void Function(T? result, String? error)`; handle both result and error in `onResult`.
- **`FooByUid` / `FooByP2PName` return `Future`s**: internally they go through `Framework.uidCallAsync` / `Framework.p2pnameCallAsync`.
- **`uid` type**: `Uint8List(32)`; `uid.length != 32` raises `RangeError`.
- **`BridgeHost.start()`**: must be called first to load the FFI bridge.
- **`BridgeHost.instance.stop()`**: must be called before the process exits.

## 4. Cross-language interoperability cautions

### 4.1 Endpoint consistency

The Call library in every language connects by default to:

```
ipc:<Unit>_abi
```

The App name defaults to `<Unit>_abi`, the P2P group name to `<Unit>_service_test_p2p`. **Both sides must be generated from the same source unit**, otherwise the API names and type tables will not match.

### 4.2 UID passing

| Language | UID type |
|------|----------|
| Pascal | `TP2P_UID___` (32-byte array) |
| Python | `bytes` / hex string / `{bytes: Uint8Array(32)}` |
| C++ | `std::array<std::uint8_t, 32>` |
| C# | `P2PUid` |
| Rust | `lingofuse::uid::Uid` |
| Go | `sys.TP2P_UID` (an `[32]byte` wrapper) |
| Java | `byte[]` |
| Node.js / TS | `Uint8Array(32)` or a hex string |
| Erlang | `<<_:256>>` (a 32-byte binary) |
| Julia | `NTuple{32, UInt8}` |
| Zig | `lf.Uid` |
| Swift | `Uid` |
| Ruby | `String` (32 bytes of binary) |
| Fortran | `integer(c_int8_t)(LF_UID_BYTE_COUNT)` |
| Dart | `Uint8List(32)` |
| R | `raw(32)` |

When passing a UID across languages, serialize it to a **64-character hex string** first and parse it in the target language; that is the only unambiguous form in every language.

### 4.5 Thread model

The async callbacks in every language execute on a **worker thread**. **Do not call blocking LingoFuse interfaces inside a callback** (that causes a deadlock), and do not manipulate the UI directly.

If a callback needs to get back to the main thread:

- **Pascal / Delphi**: `TThread.Synchronize` / `TThread.Queue`
- **C#**: `SynchronizationContext.Post` or `TaskScheduler.FromCurrentSynchronizationContext()`
- **Java**: `Platform.runLater` (JavaFX) / `SwingUtilities.invokeLater` (Swing)
- **Swift**: `await MainActor.run { ... }` or `DispatchQueue.main.async { ... }`
- **Python**: `loop.call_soon_threadsafe` (asyncio)
- **JS / TS / Node.js**: single-threaded by nature; if you use `await` in callbacks, mind the Promise chain context

## 5. Frequently asked questions

### Q1: Why do Fortran and R not support asynchronous calls?

The Fortran and R ecosystems have no **fiber / coroutine / async runtime** mechanism aligned with the LingoFuse worker model; forcing callbacks in would break the data-flow style of those two languages (Fortran's pure functions + explicit `rc`, R's vectorized evaluation). The generator therefore emits only **3 synchronous call variants** and **3 synchronous notify variants** (app / uid / p2p) for them.

If you need concurrency:

- **Fortran**: use OpenMP or `!$omp parallel`, calling the synchronous interface independently on each thread; or use a thread pool.
- **R**: use the `parallel` / `future` package; each worker starts its own LingoFuse runtime (`lf_load`).

### Q2: Why does Erlang have no sequenced async?

The Erlang generator only produces `_async`, `_uid_async` and `_p2p_async`, with **no `_async_sequenced`**. Erlang's async model is "spawn a Collector process that receives `{lf_async_result, Ref, ...}` messages", which has no notion of "ordering". If you need ordering:

- use a `gen_server` to serialize the calls;
- or explicitly deliver the results to the same `gen_server` from the async callback.

### Q3: Is there a difference between asynchronous and synchronous notify?

**No**. notify by definition means "send and do not wait for a reply", so whether it is `Foo` or `Foo_SequencedNotify`, the caller returns immediately. The only difference is **the service-side processing order**:

- `Foo`: the service may handle it concurrently on multiple worker threads;
- `Foo_SequencedNotify`: LingoFuse guarantees that multiple notifies on the same connection are delivered in call order.

### Q4: In which languages are the UID variants available?

**All 17 languages** support them. But **Fortran / R only support synchronous UID** (no UID async); **Erlang has `_uid` and `_uid_async` but no `_uid_async_sequenced`**. See [§2.1](#21-variant-counts).

### Q5: Do I need different TargetApps when calling multiple services in one process?

Yes. `ABI_TargetApp` (named differently per language) is a **global configuration**; to call two services at once you must **change `TargetApp`** before each call, or:

- use the UID / P2P group name variants (they bypass `TargetApp`);
- use separate call library instances (**not recommended**, since it loads the runtime twice).

### Q6: What should I watch out for when deploying across platforms?

- **UID byte order**: a UID is **32 opaque bytes** and has no byte-order issue; passing it as a hex string is recommended.
- **String encoding**: the call libraries in every language encode strings as **UTF-8**; there is no ambiguity in cross-language calls.
- **Numeric types**: `int64` / `uint64` may lose precision in JS / TS / Erlang / Ruby (JS / TS use `bigint`, Ruby uses `Integer`, Erlang uses `integer`); make sure the generator output uses the correct type.
- **NaN / Infinity**: float `NaN` / `Infinity` can be transmitted at the binary level; the JSON path does not support them, but the ABI path **does**.
- **Empty string vs null**: the call libraries in every language encode strings as "`NUL`-terminated UTF-8 bytes"; an **empty string** encodes as a single `NUL` byte; a **`null` string** has **no semantics** on the ABI path (an empty string must be used instead).

### Q7: Does calling LingoFuse inside a callback deadlock?

Yes. **Callbacks run on worker threads, and the worker thread pool has a fixed size**. If a callback synchronously calls `LF_Call` / `LF_Notify`, it occupies worker threads while waiting for another worker thread, causing a deadlock.

**Correct approach**:

- **dispatch the LingoFuse call inside the callback to a separate thread** (`std::thread` / `TThread.CreateAnonymousThread` / `Task.Run` / `Thread` / `spawn` etc.);
- or switch to the async interface so the callback itself does not block.

### Q8: Can I modify the generated call library by hand?

You can, but it is **not recommended**. The generator regenerates all files according to **the current state of the source unit**; if you change `<Unit>_abi_call.<ext>`, regeneration overwrites it. To customize:

- use a **wrapper**: write another layer on top of the generated library;
- or put the custom logic in `internal_call_<Api>` (service side) rather than the call side;
- or patch the generator (see `code_decl_to_abi_OPERATIONS.md`).

### Q9: Why does Python have `_Aio` while other languages do not?

Python's `async/await` is a **native language feature**, so `async def` functions can be generated for the user to `await` directly; the async models of other languages (Go's goroutines, Rust's `Future` trait, C#'s `Task`, Swift's `async`, etc.) are closer to LingoFuse's callback model and only need wrapping in callback / Future / Promise / Task. Python's `_Async` (returning `CallFuture`) and `_Aio` (`async def`) complement each other: the former suits non-asyncio scenarios, the latter suits asyncio applications.

### Q10: Can the C# / Java call libraries be used with WPF / WinForms / Android?

**Yes**, but mind the **threading**:

- **WPF / WinForms**: async callbacks run on worker threads; UI updates need `Dispatcher.Invoke` / `Control.Invoke`. Using `await` so the compiler automatically resumes on the UI thread is recommended (WPF / WinForms `SynchronizationContext` handles it).
- **ASP.NET Core**: there is no `SynchronizationContext`, so after `await` you are still on a worker thread; avoid relying on thread-local state.
- **Android**: async callbacks run on worker threads; UI updates need `runOnUiThread` / `Handler(Looper.getMainLooper())`.
